## 3. 关键改动：把"策略"从"查价"里拆出来

### 3.1 问题

原来折算钩子的门禁顺序是：

```
net → 空堆叠 → 总开关 → 读档守卫 → 【EMC 表就绪】 → 是否物品 → 组件策略 → 查价
```

`EMC 表就绪` 挡在"组件策略"前面，导致：

1. **无头环境测不到组件策略** —— 无头服务器上 EMC 表永远为空，根本走不到那一步；
2. 更糟的是，**这类断言本来就没法写**：无论被哪道门挡住，钩子的表现都是"原样返回"，
   光看返回值无法区分"组件策略挡住了"和"EMC 表没就绪"。

阶段 3 的自检里那条"折算门禁：EMC 表未就绪 → 不折算"就是这种**弱断言**。

### 3.2 改法

1. **抽出纯策略函数** `EmcDepositHandler.skipReason(ItemStack)`：
   返回 `null` 表示放行，否则返回人类可读的跳过原因（"被配置的黑名单/白名单排除"、
   "带非默认数据组件…"）。
2. **把廉价的结构/策略判断移到"EMC 表就绪"之前**：
   它们本来就不需要价格，提前还能省掉无谓的查表。

于是自检可以断言**具体原因**，而不是只能断言"原样返回"：

```
OK   组件策略：普通钻石剑放行；改名物品与耐久物品均被挡（原因="带非默认数据组件…"）
```

**这条经验值得推广**：当一个判断有多个可能的拒绝理由时，让函数**返回理由**而不是布尔值
—— 它同时改善可测性与可观测性（日志/命令里能直接带上原因）。

## 4. 配置项总览（8 项）

### `[deposit]`

| 项 | 默认 | 说明 |
|---|---|---|
| `enableEmcDeposit` | `true` | 折算总开关 |
| `convertComponentItems` | `false` | 是否折算带组件的物品（**打开会销毁附魔/耐久/容器内容物**） |
| `emcDepositBlacklist` | 空 | 命中不折算。支持 `minecraft:diamond` 与 `#minecraft:swords` |
| `emcDepositWhitelist` | 空 | 非空时只折算命中的，优先级高于黑名单 |

### `[exchange]`

| 项 | 默认 | 说明 |
|---|---|---|
| `showVirtualEntries` | `true` | 是否显示"无库存可兑换"的条目 |
| `exchangeRequiresKnowledge` | `true` | 兑换是否必须命中学习集合 |
| `maxExchangePerClick` | `Long.MAX_VALUE` | 单次点击上限 |
| `exchangeFeedback` | `NONE` | 成功提示：`NONE`/`CHAT`/`ACTION_BAR`（失败始终走聊天栏） |

所有 getter 都在配置未加载时返回**默认值**而不是抛异常 —— 因为折算钩子挂在 BD 的存储插入路径上，
配置读取失败不该把整条插入路径炸掉。

## 5. 卸载风险（写进 README 的核心内容）

**移除本模组会让所有维度网络里的 EMC 归零。**

原因：EMC 以"自定义资源类型"存在 BD 的网络存储里，而 BD 对未注册类型会在反序列化时
`catch(Throwable)` **静默丢弃条目**（`AbstractUnorderedStackHandler.java:889-898`）。
存档不会损坏，但那部分 EMC 无声消失。

已写进 `README.md` 的「卸载前必读」一节，并给出建议：卸载前用
`/beyondemc exchange <物品> <数量>` 把 EMC 换成物品。

## 7. 关于"性能"这项的处理说明

路线图里写的是"性能检查：`getSellValue` 在批量插入时的开销；**必要时**加价格缓存并在
`EMCRemapEvent` 失效"。

**本轮没有加缓存**，理由是：

1. 加缓存需要引入一份"物品→价格"的副本 + 失效逻辑，而我们刚刚在阶段 5 连续两次
   因为"多维护一份状态"而踩坑（见 `phase5-report.md` §7.10、§7.11）；
2. `IEMCProxy.getValue/getSellValue` 对**无组件物品**（我们的默认折算对象）就是一次 map 查表，
   本身不慢；真正昂贵的是带组件的物品走 `DataComponentProcessor` 链，而它们默认**不折算**；
3. **没有测量就优化**违背本项目一贯的纪律。合理的做法是在阶段 7 用一次性大批量插入
   （例如漏斗灌 10 万件）实测 tick 耗时，**如果**真的成为瓶颈再加缓存，并同时补上
   `EMCRemapEvent` 失效的自检。

这条决定记录在案，避免后来者误以为"漏做了"。
