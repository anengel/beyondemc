## 3. 决定性证据 A：直接解析存档

**被测对象**：`run/saves/新的世界/data/BDNet_0.dat`（2026-10-01 15:45 由客户端退出时写入，774 字节 → gunzip 后 3603 字节）。

**解析结果**：18 个存储条目 = 1 条 EMC 池 + 14 条 `emc_item` + 3 条 BD 原生物品条目。

EMC 池 = **3 066 234**。14 条物化条目：

判定方法：条目数量 `n` 一旦给定，能产生它的价格 `p` 必须满足
`n × p ≤ EMC < n × (p+1)`，即 `p ∈ [⌊EMC/(n+1)⌋+1, ⌊EMC/n⌋]`。下表区间由脚本算出（§7.1）。

| 物品 | 条目数量 `n` | 反推的价格区间 | 候选数 | 判定 |
|---|---|---|---|---|
| `minecraft:stick` | 766 558 | **[4, 4]** | 1 | ✅ 唯一，且日志独立确认 4 |
| `minecraft:oak_planks` | 383 279 | **[8, 8]** | 1 | ✅ 唯一，且日志独立确认 8 |
| `minecraft:lantern` | 13 159 | **[233, 233]** | 1 | ✅ 唯一 |
| `minecraft:redstone_torch` | 45 091 | **[68, 68]** | 1 | ✅ 唯一 |
| `minecraft:soul_campfire` | 19 530 | **[157, 157]** | 1 | ✅ 唯一 |
| `minecraft:spruce_fence_gate` | 95 819 | **[32, 32]** | 1 | ✅ 唯一 |
| `minecraft:diamond` | 374 | [8177, 8198] | 22 | ✅ 日志独立确认 **8192**，且落在区间内 |
| `minecraft:diamond_pickaxe` | 124 | [24530, 24727] | 198 | ✅ 日志独立确认 **24584**，且落在区间内 |
| `minecraft:shulker_box` | 737 | [4155, 4160] | 6 | ✅ |
| `minecraft:golden_apple` | 185 | [16486, 16574] | 89 | ✅ |
| `minecraft:diamond_sword` | 187 | [16310, 16396] | 87 | ✅ |
| `minecraft:emerald` | 187 | [16310, 16396] | 87 | ✅（16384 在其中） |
| `minecraft:enchanting_table` | 182 | [16756, 16847] | 92 | ✅ |
| `minecraft:netherite_axe` | 34 | [87607, 90183] | 2577 | ✅ |

其中 **6 项的价格被存档唯一确定**（区间只有一个整数），**2 项另有日志独立给价**（钻石 8192、
钻石镐 24584）且都落在区间内 —— 这 8 项构成精确恒等式 `n = floor(EMC ÷ p)`；
其余 6 项的数量同样落在"该数量对应的价格区间"内，无一项越界。

**结论**：

1. **物品真的存在**：它们不是界面上的显示行，而是 `UnifiedStorage` 里带自定义键类型的真实条目，
   由 BD 自己持久化、同步、参与合并。
2. **口径正确**：8 项（6 项价格唯一 + 2 项日志给价）出现精确恒等式 `数量 = floor(EMC ÷ 单价)`；
   其余 6 项的数量也都落在"该数量对应的价格区间"内，无一项越界。
   注意 14 项**各自独立取整**（不是"取完一个再扣 EMC 算下一个"）—— 这正是需求里
   "钻石 2 个 + 泥土 100 个"那种并列口径。
   这正是"**按 EMC 总额、各物品彼此独立、逐件向下取整**"的定义。
3. **不塌缩**：14 条同类型（`emc_item`）条目各自独立存在、数量互不相同。
   若 `EmcItemKey` 没有覆写 `equals`/`hashCode`（BD 的 `LongStackKey` 比的是 `getTypeId()`），
   这 14 条会被 `HashMap` 合并成 1 条 —— 存档里看到 14 条，等于从存储层证伪了塌缩。
4. **真实库存优先**：同存档里另有一条**原生** `minecraft:shulker_box` 条目（装着 8 把效率 II 下界合金斧），
   与物化的 `shulker_box` 并存而不互相顶掉 —— 因为带容器组件的物品归一化后是不同的 `ItemInfo`。

## 4. 决定性证据 B：取出确实扣费（S-0.3-7 的收费侧）

`S-0.3-7` 的担忧是：物化条目会不会从某条 BD 抽取路径"白拿"。三条入口逐条查证：

| 入口 | 证据 | 结论 |
|---|---|---|
| GUI 点击 / 吸附 | 日志 `拦截物化条目点击：minecraft:diamond_pickaxe ×1，意图=PICKUP_TO_CURSOR`（4 次）等 7 次；源码 `ExchangeService.pickupToCursor` 是**先 `spendEmc(cost)`、后 `setCarried(...)`**，扣不够就回滚并返回失败 | ✅ 收费 |
| 网络接口（**按槽位**） | 日志 **7 条** `接口兑换：… → 扣除 N EMC（单价 P，网络 0）`：钻石 ×1 扣 8192（5 次）、木棍 ×1 扣 4（2 次） | ✅ **有价格的实测扣费** |
| 按标签 | 收费侧未在本次日志中出现；**拒绝侧**由自检覆盖（`extract(TagKey,…)` 外部抽取被拒 + 正控证明标签确实解析到物化条目） | ⚠️ 收费侧待补 |

交付前把关（不是先扣钱再失败）也有实证：

- `鼠标上的堆叠已经满了`（`ExchangeService:300` 的拒绝理由）以聊天消息形式出现在日志里，且 EMC 未被扣 —— 属于容量不足而非余额不足；
- `ExchangeService` 的发放路径有"只按实际发放数量收费 + 没发出的部分原价退回"两条兜底。

**余额不足**这一条本次没有直接观测到（没有构造该场景）。

## 6. 决定性证据 D：A/B 存档往返回退演练（本轮新做，无头可跑）

同一份存档（0.3.1 写的 `BDNet_0.dat`，含 14 条 `emc_item`）分别交给两个版本读：

| 版本 | 启动 | 14 条 `emc_item` | EMC | 学习集 |
|---|---|---|---|---|
| **0.2.0**（`git worktree` 检出 tag `v0.2.0` 后 `runServer`） | `Done (0.346s)!` —— **不崩** | 逐条 WARN：`解码第 N 个新格式条目时出错: java.lang.IllegalArgumentException: 注册表中不存在此类型的Key，请先注册再使用: beyondemc:stack_type/emc_item`（14 条）→ **优雅丢弃** | 3066234 **无损** | `读回网络 0 的已学习物品 14 项` ✅ |
| **0.3.1**（本项目 `runServer`） | `Done` | **0 条解码错误**（14 条全部解码成功） | 3066234 | `读回网络 0 的已学习物品 14 项` ✅，自检 0 FAIL |

**回退安全性结论**：

- 拿 0.3 的存档去跑 0.2 的代码：**不崩、不报异常、EMC 与学习集完整**；
  只有物化条目被丢掉（BD 的既定行为：未注册的键类型在反序列化时被丢弃）。
- 丢掉的是**派生数据**，不是价值：EMC 池还在，0.2 会用它重新算出虚拟条目，
  回到 0.3 也会按 EMC 重新物化。所以"退回 0.2 再升回 0.3"是无损往返。
- 日志里那行 `WARN` 是 BD 自己打的（`BeyondDimensions`），不是我们的 —— 属于"可观测的优雅降级"。

> 复现命令见 §7.2。注意：把存档**反过来**（0.3 读 0.2 存档）不必单独做 ——
> 本次真人试玩的整个世界（`新的世界`）就是 0.2.0 时期建的。

### 补充：0.3.1 自己的回写往返（同一份存档）

把同一份存档铺给 0.3.1 的专用服务器，**不碰任何东西**，等它跑完一次自动保存
（默认 6000 tick）后比对：

| 时刻 | 谁写的 | 文件 | 条目 | emc_item | EMC |
|---|---|---|---|---|---|
| 15:45:30 | 客户端（退出时保存） | `run/saves/新的世界/data/BDNet_0.dat` | 18 | 14 | 3066234 |
| 16:02:27 | 专用服务器（自动保存） | `run/world/data/BDNet_0.dat` | 18 | 14 | 3066234 |

**14 条物化条目的物品与数量逐项完全相同**（程序化比对，`True`）。

这补齐了持久化链路的最后一环：**写 → 读 → 再写** 不丢任何东西，
也就说明"物品真实存储于维度网络"这句话在存档层面成立，而不是"内存里有、下次就没了"。

## 7. 复现方法

### 7.1 解析存档（不需要启动游戏）

```bash
python tools/nbtdump.py "run/saves/新的世界/data/BDNet_0.dat"
```

`tools/nbtdump.py` 是最小 NBT 解析器（只依赖标准库），用于离线核对
"条目在不在、数量对不对"。**发布前核对物化口径时，这是最省事的办法**：
把 `floor(EMC ÷ 单价)` 与文件里的数量比一遍即可。

### 7.2 回退演练

```bash
# 1) 在仓库外检出一份旧版本（不要用主工作区！）
git worktree add ../mod-learn-rollback-020 v0.2.0

# 2) 前置 jar 不进 git，需要手工搬
cp -r libs/ ../mod-learn-rollback-020/libs/

# 3) 把要试的存档铺成"专用服务器的世界目录"
mkdir -p ../mod-learn-rollback-020/run/world
cp -r "run/saves/新的世界/." ../mod-learn-rollback-020/run/world/
printf 'eula=true\n' > ../mod-learn-rollback-020/run/eula.txt

# 4) 跑（必须显式指定 GRADLE_USER_HOME，否则会去下 1.6 GB 的 ~/.gradle 冷缓存）
cd ../mod-learn-rollback-020
JAVA_HOME='C:\Program Files\Java\jdk-21.0.12.1' \
GRADLE_USER_HOME='C:\mc\mcwj\mod-learn\.gradle-home' \
  cmd //c "gradlew.bat runServer --console=plain"   # 看 Done / 解码第 N 个条目出错

# 5) 收工
git worktree remove --force ../mod-learn-rollback-020
```

判定标准：**出现 `Done (...)` 即不崩**；`解码第 N 个条目出错` 的条数 =
该版本不认识的条目数（0.2.0 应为 14，0.3.x 应为 0）。

### 关于 EMC 账目的一处说明

日志里 `折算：…`（存入换 EMC）只打印**前 3 次**（`EmcDepositHandler.LOG_FIRST_N = 3`），
`物化（第 N 次）`也只打印前 8 次。所以本次日志**无法**完整重算整条 EMC 流水；
但 §3 证明**终态**是自洽的（14 条数量全部落在对应价格区间内、无一项越界）。
这类"取几条日志 + 终态校验"的组合足够判定正确性 —— 除非某次操作的**净额**恰好为 0，
否则终态不可能同时满足十四个恒等式。
